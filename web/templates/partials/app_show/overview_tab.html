Docker Build Cache Guide

Why builds re-run from scratch and how to keep them fast with layer caching

How Docker layer caching works:

Docker builds and caches images top-to-bottom. If any instruction's files change, Docker invalidates that layer and all subsequent layers, forcing them to re-execute from scratch.

1

Install dependencies BEFORE copying application code

Never place COPY . . before package managers (npm install, pip install, go mod download). Any source file edit changes the hash and makes Docker download and install all libraries again.

❌ Bad (Busts cache on every edit):

COPY . .
RUN pip install -r requirements.txt

✅ Recommended (Cached):

COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .

Universal Pattern by Ecosystem:

  • Node.js: COPY package*.json ./ → RUN npm ci → COPY . .
  • Go: COPY go.mod go.sum ./ → RUN go mod download → COPY . .
  • PHP: COPY composer.* ./ → RUN composer install ... → COPY . .
  • Rust: COPY Cargo.* ./ → compile dummy build → COPY src ./src
2

Always include a complete .dockerignore file

Without .dockerignore, local temporary files like .git/, .env, local virtual environments, and log files are sent into the build context. Their timestamps and checksums change constantly, breaking Docker build cache on every single deploy. 

.git
.env
__pycache__
*.pyc
node_modules
venv
.venv
*.log
*.sqlite3
3

Tag shared images in multi-service compose stacks

If your docker-compose.yml has multiple services (e.g. web and worker) building from the same directory (build: .) without an image: tag, Docker builds two separate images sequentially.

services:
  web:
    build: .
    image: myapp:latest
  worker:
    image: myapp:latest # Reuses the image without a second build
